# Task 4: AI 辅助告警诊断（方案草案）

**Status:** in-progress

## 目标

现场操作员在运行态选中一条 Active Alarm，主动发起“智能分析”。系统基于可核对的设备数据和故障资料，给出可能原因、证据、建议检查步骤与不确定性。它只提供辅助判断，不控制设备。

这项能力应成为可以讲清楚的数据闭环：选中告警 → 获取证据 → 调用分析工具 → 生成有来源的建议 → 用固定故障案例验证质量。

## 启动 Task 4 时的现状

- `resolveActiveAlarms` 在 Web Renderer 中依据已发布 PageSchema 和实时 Data Point 计算活动告警；目前没有持久化告警事件或发生时间。
- FastAPI 的 `TelemetryHub` 在内存中保存每个 `dataKey` 的最新数值，只向订阅页面广播 Snapshot 和 Update。
- `TelemetrySession` 的最近 60 秒 Trend Sample 只属于当前运行会话，不能作为服务端可查询的历史证据。
- PostgreSQL 当前保存 PageSchema 草稿及发布版本，没有设备资料、故障手册或遥测历史表。

## 推荐的最小切片顺序

1. **证据底座**：为模拟设备保存有限时间窗的遥测记录；定义告警触发与恢复的时间点，并提供按设备、Data Point 和时间范围查询的只读接口。用固定故障序列验证“告警前后”查询确有数据。
2. **诊断接口**：操作员选择 Active Alarm 后，后端按页面发布版本和告警条件获取证据，再通过受限只读工具查询设备信息、时间窗数据与一份本地故障手册。输出结构化分析，包括证据引用和“证据不足”。
3. **UI 原型与实现**：在唯一 HTML 原型中设计“智能分析”入口和分析面板。用户批准后才修改 Vue；保留现有 Web 与 Electron Renderer 复用关系。
4. **固定案例评估**：至少覆盖温度越界、设备故障、数据过期/证据不足和恢复后告警消失。评估工具选择、证据引用与是否编造未提供的事实。

## 首版边界（建议）

- 只由操作员点击触发分析；不自动触发、不自动控制设备。
- 分析结论必须区分“观测事实”“可能原因”“建议检查”，并明确数据时间与 Data Freshness。
- 手册先使用项目内可审查的模拟设备资料；不把模型知识当作设备事实。
- 不引入通用聊天、多设备调度、自动工单、告警确认或真实工业控制协议。
- 模型提供方与具体 Agent/RAG 库在证据接口和评估案例明确后选择。

## 已确认的首个开发切片

用户确认先做可持久查询的告警证据。服务端按接收时间保存 Telemetry Observation；设备上报的时间戳原样保留，用于追溯，但不作为服务器排序与 Data Freshness 的依据。只读查询从当前已发布 PageSchema 验证 Alarm Condition，并返回页面版本、有限时间窗内的观测和能由相邻观测证明的 Alarm Transition。当前版本发布前的观测不参与该版本条件的转折计算。窗口内第一条记录已经触发且没有更早基线时，起点保持未知。

首版查询窗口最长 15 分钟、最多返回 1000 条观测；演示数据保留 24 小时。该切片不修改运行态 UI，也不调用模型。

## 当前进度

证据底座已完成：遥测观测写入 PostgreSQL；只读接口按当前发布版本校验条件、返回观测及可证实的触发/恢复转折，缺少基线时保留未知起点。Task 4-02 接下来定义诊断输出合同和固定故障案例，并先在唯一 HTML 原型中验证操作员界面。

## 验收目标

- 操作员能从一条当前告警发起分析，看到与该告警、页面发布版本和设备数据对应的证据。
- 每条事实引用可追溯到具体时间段的数据或故障资料；证据缺失时明确说明。
- 固定故障案例可重复运行并检查分析结果。
- 用户能解释数据从模拟器到告警、证据查询、分析输出的调用链。
