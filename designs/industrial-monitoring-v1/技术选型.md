## 2. 核心架构决定

### 2.1 一个 Web 应用，两个独立路由

第一版不创建 `editor-web` 和 `runtime-web` 两套应用，而是在一个 Vue 应用中提供：

- `/editor/:pageId`：编辑态。
- `/runtime/:pageId`：运行态。

两者都是独立页面入口，但共用 `renderer-core` 和 `components-web`。等出现独立部署、不同权限或不同发布节奏后，再拆成两个应用。

这样比一开始复制两套 Vite 工程更简单，也仍然能够证明“编辑态和运行态共享组件协议”。

### 2.2 使用 DOM Renderer，不使用 Canvas/Konva/Fabric

组件节点使用绝对定位和 CSS `transform`。指标卡、文本、ECharts、设备状态和告警列表仍然是真实 Vue 组件。

```text
Page Schema
    │
    ▼
Renderer Core：解析布局、数据绑定、能力检查
    │
    ▼
Component Registry：type → Vue component
    │
    ├── 编辑态：Renderer + SelectionOverlay + Moveable
    └── 运行态：Renderer
```

选择 DOM 的原因：

- ECharts、文本、表格和表单天然适合 DOM。
- 编辑态和运行态可以渲染同一个 Vue 组件实例定义。
- 浏览器调试、事件处理、可访问性和响应式布局更直接。
- 第一版没有上千图元、复杂连线或高频矢量绘制，不需要 Canvas 引擎。

当真实压力测试证明 DOM 节点数量成为瓶颈，再考虑把特定工业图形层下沉到 Canvas，而不是现在整体更换渲染模型。

### 2.3 Schema 是跨端合同，不是 Pinia 状态快照

Schema 只描述可发布内容：

```text
PageSchema
├── version
├── canvas: width / height / background
└── components[]
    ├── id / type
    ├── position / size
    ├── props
    └── bindings
```

以下内容不进入发布 Schema：当前选中组件、属性面板展开状态、缩放比例、鼠标位置、撤销栈和未提交输入。

TypeBox 负责同时生成 TypeScript 静态类型和标准 JSON Schema；Ajv 在浏览器中校验导入、保存和运行态加载的数据。后端保存 Schema 前，再使用 Python `jsonschema` 对同一份 JSON Schema 做一次校验。

这比只写 TypeScript interface 更可靠：interface 在运行时会消失，也无法直接给 Python 后端使用。

## 3. 前端选型

| 层 | 选择 | 用途与边界 |
|---|---|---|
| 基础框架 | Vue 3.5 + TypeScript | 延续你的 Vue 经验，使用 Composition API 和严格类型 |
| 构建工具 | Vite 8 | 开发服务器和生产构建；单独运行 `vue-tsc` 做类型检查 |
| 路由 | Vue Router 5 | 编辑态、运行态和后续登录页面 |
| 状态 | Pinia 4 | 编辑器文档、选中状态、撤销栈；服务端数据仍通过 API Repository 获取 |
| UI 控件 | Element Plus 2 | 属性表单、按钮、弹窗；画布和指标卡保持项目自定义样式 |
| 拖拽缩放 | vue3-moveable 0.28 | 只负责选中组件的拖动、缩放和后续旋转，不拥有业务 Schema |
| 图表 | ECharts 6 | 第二阶段折线图组件；第一任务不提前引入 |
| Schema | TypeBox 1 + Ajv 8 | Schema 定义、TS 类型推导、运行时校验 |
| 测试 | Vitest 5 + Playwright 1.63 | 单元/组件测试和编辑器到运行态的关键链路测试 |
| 样式 | CSS Variables + SCSS | 复现已通过的工业视觉；不引入 Tailwind |

Vue 官方建议使用 Vite 驱动的 TypeScript 项目，并明确说明 Vite 的转换过程不负责完整类型检查，因此 CI 中必须单独运行 `vue-tsc`。[Vue TypeScript 指南](https://vuejs.org/guide/typescript/overview.html) · [Vite 指南](https://vite.dev/guide/)

### 状态职责

```text
Pinia editorDocumentStore
├── draftSchema
├── selectedIds
├── viewport
├── history
└── actions: updateProps / move / resize / undo / redo

Renderer Core
├── validateSchema
├── resolveComponent
├── resolveBinding
└── calculateLayout
```

不要让 Renderer 直接依赖 Pinia。运行态只需要传入 Schema 和数据快照就能渲染。

## 4. 后端选型

| 层 | 选择 | 用途与边界 |
|---|---|---|
| Python | 3.12 | 当前生态成熟，避免把项目建立在最新解释器兼容性上 |
| 包管理 | uv | 管理虚拟环境、依赖和锁文件 |
| API | FastAPI 0.141 | REST、OpenAPI 和 WebSocket |
| DTO | Pydantic 2 | 普通请求/响应模型，不重复定义 Page Schema |
| ORM | SQLAlchemy 2 | 明确的数据模型与事务边界 |
| 迁移 | Alembic | 可复现数据库结构 |
| 驱动 | psycopg 3 | PostgreSQL 连接 |
| 数据库 | PostgreSQL 18 | 项目/页面使用关系表；版本化页面 Schema 使用 JSONB |
| 测试 | pytest 9 | API、权限、事务和 Schema 合同测试 |

FastAPI 官方支持 WebSocket；第一版直接使用标准 WebSocket，不增加 Socket.IO 协议层。[FastAPI WebSocket](https://fastapi.tiangolo.com/advanced/websockets/)

PostgreSQL 的 `jsonb` 会以分解后的二进制格式存储 JSON，适合后续查询和索引；页面版本仍需先通过 Schema 校验，不能把 JSONB 当成无结构垃圾桶。[PostgreSQL JSON 类型](https://www.postgresql.org/docs/current/datatype-json.html)

### 最小数据模型

```text
Project

Page
├── id

├── name
```

第一阶段先用浏览器本地存储跑通编辑器；第二阶段接入这些表。不要在第一任务里同时写数据库。

## 5. 实时数据协议

第一版使用：

```text
Python Simulator
       │
       ▼
FastAPI Telemetry Hub
       │ WebSocket
       ▼
Web Runtime
       │ dataKey 匹配
       ▼
Component Registry
```

消息保持最小：

```json
{
  "type": "telemetry.update",
  "timestamp": 1789171200000,
  "values": {
    "pump1.outlet_temp": 68.4
  }
}
```

前端每一帧合并收到的更新，再批量写入运行时数据 Store，避免每条消息直接触发每个组件重渲染。

第一版不选 MQTT：当前模拟器、API 和浏览器都由我们控制，WebSocket 已足以证明实时数据链路。以后接真实工业设备时，在后端新增 MQTT Adapter，前端协议不变。

## 6. Electron 与小程序

### Electron

第二周再加入 Electron 44 + electron-vite 5。Electron 只作为现有 Web 编辑器的桌面壳：

```text
Main Process → 窗口、文件、更新
Preload       → 暴露白名单 IPC
Renderer      → 复用 Vue 编辑器
```

Vue 组件不能直接调用 Node API。Electron 官方将主进程和渲染进程明确分开，渲染进程应按 Web 标准工作。[Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)

### 小程序

第二周使用 uni-app Vue 3 + TypeScript。小程序只共享：

- Schema JSON
- 数据协议
- 组件名称和属性含义
- 校验样例

不共享 Web Vue 组件和拖拽代码。uni-app Vue 3 编译器基于 Vite，但不同平台仍有各自运行时，因此“共享协议、不强行共享 UI”更可靠。[uni-app 跨端原理](https://uniapp.dcloud.net.cn/tutorial/)

## 10. 明确排除的方案

| 暂不选择 | 原因 |
|---|---|
| Fabric.js / Konva | 当前组件以 DOM、ECharts、文本和列表为主，会增加编辑态与运行态复用成本 |
| 两套 Web 工程 | 三周期限内重复路由、主题、权限和构建配置，没有收益 |
| NestJS / Spring Boot | 都可实现，但会分散 Python 后端求职主线 |
| Socket.IO | 原生 WebSocket 已满足当前协议，没必要增加专用客户端和服务端协议 |
| MQTT / Kafka | 没有真实设备接入和消息规模证据，第一版属于提前设计 |
| Turborepo / Nx | 当前 workspace 规模小，普通 pnpm scripts 足够 |
| Redis / Celery | 暂无跨进程任务、缓存或队列需求 |
| 微前端 | 一个作品、一个团队、一个发布节奏，不具备采用条件 |
| Tailwind | 已通过的设计依赖明确的工业视觉变量和局部样式，SCSS 更直接 |
